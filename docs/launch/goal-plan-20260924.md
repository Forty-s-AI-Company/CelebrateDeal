### WP-A/B：Git 整理與部署映射

1. 列出 tracked/untracked 與 worktree ownership，保存 sanitized 摘要。逐項 review 後精確 `git add -- <paths>`；禁止 `git add .`、丟棄未知變更或清掉別人 worktree。
2. 重新 fetch 並讀 live refs。比較 PR #210/#211、master、本機 dirty diff，辨識已等效合入的功能。不得以 553 commits 全部重播，也不得只挑容易通過的片段漏掉必要功能。
3. 可建立 `codex/*` 整合分支或獨立 worktree，先保存已盤點的精確 scope checkpoint，再依 diff 選擇 merge/cherry-pick/移植；不用 reset、clean、stash、restore、checkout 或 rebase 丟棄未知內容。
4. 「全部整合」指本次相關產品、測試與文件；已被取代或舊 smoke 項列出理由。不刪未確認的分支/worktree，不擅自關閉仍有獨有工作的 PR。
5. 查證兩個 Vercel project、部署 target、production branch、自動部署規則與 staging alias。確認 merge 不觸發正式部署；若有副作用，先用可審查且限定本次的非prod隔離方式處理，不能確認就不執行該副作用。
6. 部署前核對 DATABASE_URL 與 DIRECT_URL 同屬 staging 隔離資料，不顯示值。`vercel.staging.json` 只覆寫 DIRECT_URL 不能當成資料隔離證明。staging migration 需查 pending 清單、向後相容性與備份/回復方式，禁止盲跑破壞性 migration。
7. 同時確認實際使用的 Auth、Storage/video provider project/bucket、PayUni Sandbox merchant/callback 均對應固定非 Production 資源；若使用 Supabase，包含其 project identity 與 NEXT_PUBLIC_SUPABASE_URL 綁定。以既有 identity/binding gate 或 sanitized project fingerprint 證明，不列舉 Secret。未確認的資源不執行登入/上傳/checkout 等 mutation 或部署；未使用的 provider 不憑空新增前置條件。

### WP-E/F：合併、部署與驗收

1. PR 必須基於最新 master、無 conflicts、無未解核心 BLOCKER/MAJOR；等實際 required context `quality` 綠燈，依 branch protection 合併。不用 force push、admin bypass 或直接推 master。
2. CI 必須包含本輪最終 candidate。合併後若 tree 與受測 tree 不同，重跑受影響 gates；不得用歷史 dirty-tree PASS 代替。
3. 保留舊 staging deployment ID 與 alias 映射作回復點。在明確 staging 專案使用非prod target，部署已合併來源。可使用內容相同的 `codex/*` staging release ref，但需證明 tree digest 與 merged source 相同。
4. staging READY 後先在 immutable deployment URL 驗證可於該網址完成的主要瀏覽器流程，通過才切指定 alias。記錄 master merge SHA、build source SHA/tree digest、deployment ID、target、alias 與驗證時間；不能只用 HTTP 200 或 GitHub preview comment 證明新版。
5. 在實際 staging 瀏覽器使用合成資料檢查登入、Funnel保存發布/公開表單、商品 Sandbox checkout→callback→持久化訂單與重複 callback 冪等性、影片與主要導覽。檢查行動版基本可用、關鍵無5xx與嚴重JS錯誤。authenticated mutation只限已確認隔離資料。至少一筆固定合成 Sandbox 訂單須完成付款結果、持久化與使用者可見狀態；不得只驗證 checkout 入口。需固定 alias 的 callback 流程可在切 alias 後執行並保留回復點。
6. 若 deployment 或 smoke 失敗，alias 回復已知健康版本並記錄 failure；若 schema 不相容，先依事先設計的相容回復方案，不盲目切舊程式。回復不算新版本交付成功。

## 驗證與驗收 gate

從已批准 process environment、CI Environment 或平台 provider 注入 Secret，不讀 `.env*`。`scripts/preflight.ts` 有自動載入 env 檔行為；本機命令需透過既有 no-env mirror/controlled runner，或在不含 env 檔的乾淨 CI 環境執行，不直接以本機原始環境硬跑。

精確命令以 `package.json` 與現行 CI 為準：`npm run secret:scan`、`npm run lint`、`npm run typecheck`、`npm run typecheck:strict-index`、`npm run test:coverage`、`npm run test:contracts`、`npm run test:db:concurrency`、`npm run e2e -- --fail-on-flaky-tests`、`npm run e2e:funnel-elements`、`npm run secure:staging:contract`。受影響時跑 `test:line`、`test:interactions`、`test:automations`。DB/browser 使用獨立 disposable DB 與合成資料。

build 透過已審查的 `scripts/build/controlled-production-build.mjs` 或 CI/staging 的合法環境，保留 build模式和外部金流環境差異；不將正式 PayUni 值注入測試。受保護 CI 的其餘 gates 包含 dependency audit 仍需正常通過。`npm run qa:payuni:sandbox` 只在 callback與lineage前置條件成立時執行。

每個 WP 綁 snapshot、實際執行與 review 收據，用 MCP `assess_task`；MCP 不可用時透過 `.ai-team/mcp_server/route_cli.py` 的同一 `assess_acceptance`。`validation_runner.py` 僅最長900秒，長套件採既有可信runner/CI receipt介接，不能把timeout或零測試標PASS。若 receipt 介接不可用，記 ACCEPTANCE_BLOCKED，繼續可獨立工作，不能自造成功收據。

完成狀態分開：

- `CORE_STAGING_READY`：核心 candidate tests/review通過，protected merge成功，指定staging對應新來源且核心瀏覽器旅程成功；包含一筆Sandbox checkout→callback→持久化訂單與重複callback冪等性證據。若外部Sandbox無法驗證此核心商品訂單路徑，標為NOT_PROVEN，CORE_STAGING_READY不成立；可如實交付已更新但尚未完整驗收的staging。
- `SANDBOX_FINANCIAL_READY`：實際外部 Sandbox closure 全項有證據；未知項維持NOT_PROVEN。退款、對帳等完整financial closure的外部阻擋可列下一輪，但不得宣稱financial ready；不得用這項延期豁免CORE_STAGING_READY的成功訂單證據。
- `PRODUCTION_READY`：本輪不評定為完成。

本輪 Goal 的必需完成條件是 CORE_STAGING_READY、文件入口/缺口清單完成、相關Git工作處置明確、PayUni仍為Sandbox且closure狀態如實呈現；不以尚未排入本輪的新功能阻擋收尾。
