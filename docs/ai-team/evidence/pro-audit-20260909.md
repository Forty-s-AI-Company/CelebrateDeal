# CelebrateDeal 原生架構與資安審查

日期：2026-09-09。來源基準：`cbd47d6e`，近期變更範圍 `HEAD~5..HEAD`，90 個檔案。使用者明確改採原生語義審查與本地驗證，排除 Deep Scan 外掛。未執行部署、正式服務、外部付款／退款或正式資料修復。

## WP1：威脅模型與查核範圍

信任邊界為瀏覽器 → checkout／Server Actions → tenant-bound 資料層 → 簽章驗證後的 provider callback → Serializable 帳務、庫存與權益交易。付款成功必須由服務端驗證的 provider 狀態證明；callback metadata 不得取代原始 checkout 的權益與租戶設定。

| 標的 | 檢查與證據 |
|---|---|
| ECPay CheckMacValue | `payment-providers/ecpay.ts` 的排序、URL 編碼、SHA-256 與 constant-time 比較；既有 ECPay fixture／竄改測試。此為 ECPay 專用 MAC 規則，不誤稱標準 HMAC。 |
| Stripe webhook | timestamp + raw body HMAC-SHA256、五分鐘有效窗、provider/eventId 唯一性；`payment-webhooks.ts` 的租戶／金額／幣別驗證、Serializable re-read 與重試。 |
| 5% 含稅分拆 | `taiwan-electronic-invoice.ts`、累計折讓分拆與 safe-integer 邊界測試。 |
| 多租戶 | Portal URL slug + session vendor 綁定；課程 entitlement/customerKeyHash/course/lesson 驗證；社群 paid-member 與 post vendor 篩選；手機諮詢 action 先授權再查 tenant booking。 |
| Magic Link | HMAC、purpose、15 分鐘有效期、digest 儲存與 `consumedAt: null` 原子消耗；session 為加密 HttpOnly cookie。 |
| 個資與 server credential | checkout PII envelope、tracking credential tenant-specific 加密、傳輸 DTO、callback snapshot；檢視 PWA 離線路徑與追蹤傳輸的服務端呼叫。 |
| 諮詢與抽獎 | consultation event advisory lock + Serializable transaction；抽獎 winner compare-and-set 與 claim 原子寫入；原有併發／租戶／兌獎重放測試。 |

未確認 P0。這是近期核心攻擊面與相關原始碼的語義審查，並非對每一個資料庫 query 做形式化證明，也不宣稱全專案不存在其他漏洞。

## WP3：修補

| 風險 | 修補與回歸驗證 |
|---|---|
| P1：未付款 Checkout 被認為已付款 | `checkout.session.completed` 與 async success 僅在 payment_status=paid 時產生 paid；未結清回呼拒絕，非同步成功可開通。 |
| P1：退款累計被當作增量重複扣帳 | Charge cumulative amount 在 Serializable transaction 內與本地已退款總額比較，僅記錄差額；同額／倒序為 no-op 且標記事件已處理。測試涵蓋部分退款、兩個同時回呼、全退、重播、錯誤 PaymentIntent。 |
| P1：Stripe 後續事件缺少訂單識別 | 建立 Session 時同時寫 PaymentIntent metadata，Charge 繼承 PI 識別；所有交易 reference 使用 PI ID；建立 checkout 使用穩定 provider idempotency key。 |
| P1：退款查詢將已退款誤判為零 | expand latest_charge，核對 PI、金額與幣別，讀取 Charge.amount_refunded；缺失或不匹配拒絕。 |
| P1：加購憑證重放 | 在付款／庫存／新訂單相同交易內再次核對 paid 來源訂單，使用既有 CommerceOrderEvent 唯一鍵原子 claim。重新簽發 nonce 或不同 browser key 無法建立第二筆優惠訂單。 |
| 加購資料層／金額綁定 | 完整 Prisma Product 與 strict DTO 不相容的問題改以明確 select 修正；優惠來源改查 canonical paid order 與實付金額，避免折扣購買或商品改價高估抵扣。拒絕跨租戶與非單一品項／數量來源。 |
| 個資保存加固 | ECPay raw snapshot 改為明確對帳欄位 allowlist，移除自由訊息、自訂欄位與原始 metadata 保存；測試 exact snapshot。 |
| 稅額精度 | BigInt 20/21 整數分拆；驗證 safe-integer 上限、四捨五入誤差與總額不變。 |

沒有 schema migration 變更。獨立來源訂單對不同優惠仍依原本 kind/product 規則區分；同一優惠只兌換一次。失敗交易會回滾 claim、付款與庫存。

Stripe 行為核對來源：[Checkout fulfillment](https://docs.stripe.com/checkout/fulfillment)、[Metadata 跨物件傳遞](https://docs.stripe.com/metadata)。稅額邊界實測：9007199254740991 cents 的舊公式少算 1 cent 稅前額，整數公式得 8578285004515230 cents；此為數值精度測試，不代表資料庫允許該筆實際交易額度。

補充：claim 與本地交易失敗時一同回滾；外部 provider timeout 發生在本地交易提交後，會沿用既有 checkout 失敗處理。為避免 provider 實際已建立 session 時再次建立優惠交易，此類不確定結果不自動解除一次性 claim。

## WP4：本地驗證

環境：新建 `celebratedeal-pro-audit` 容器，PostgreSQL 16，僅綁定 `127.0.0.1:54339`，測試資料庫名稱 `celebratedeal_test`。專用 `pro_audit_migrations` schema 已套用全部 79 個 migration。固定 synthetic 加密種子僅在測試子程序使用。

原始工作站 Prisma Client 僅支援 prisma://，舊測試 DB 欄位亦過時；未改舊資料。隔離 temporary schema 產生 binary engine Client，避開另一程序持有的 Windows library engine DLL。未載入任何 .env 檔。

初次完整測試：4030 passed、5 failed、1 原有 skipped。失敗全部如實保留於本機紀錄，並修復如下：

- 根層 actions 超過 2500 行：只提取新增 tracking action，保留公開 async wrapper。
- Portal 測試缺 App Router：補 LanguageSwitcher test fixture。
- API contract registry 補三個近期 route 與兩個缺失的同路徑測試。
- schema 字距斷言改忽略水平空白，保留欄位／型別／約束文字。
- 模型／migration 清單補齊 121 models 與 79 migrations，維持逐項完整性與固定總數斷言。

核心 TAP contracts：924 passed、0 failed、0 skipped。
第二輪完整 Vitest：564 files／4041 passed、0 failed、0 skipped，316.39 秒；透過 synthetic CSRF seed 與 RT01_D2_DISPOSABLE_DB 旗標實際執行原本可選的聊天資料庫併發測試。
此全套結果早於最後的加購 canonical order 金額修補；最後修改另通過 5 項真實 Prisma／隔離資料庫測試及 72 項受影響 caller 測試，共 77 項。涵蓋折扣來源、catalogue 改價、跨租戶、多品項、多數量及既有 checkout 重放防線；未將先前全套結果當作最後版本的全套重跑。

最終原始碼版本的 `npm run typecheck`、`npm run secret:scan`（secret_scan_passed）與 `git diff --check` 均通過。原生 Reviewer 最終唯讀校核 canonical resolver、四個 caller 與交易內 claim，未發現新增 P0／P1 阻斷缺陷；Reviewer 未自行重跑資料庫測試。

新增／修改的金流與稅額檔案 ESLint 通過。checkout route 與 root actions 的既有 complexity 錯誤經 HEAD 比對確認仍存在，沒有降低 lint 規則或新增 suppression；不宣稱全專案 lint 綠燈。既有 GitHub Actions 已於每次 push 執行 lint、typecheck、secret scan 與測試，無需建立重複 workflow。
