- 基線：`review-baseline-2026Q4` = `78621ca3`（`git rev-parse HEAD` 與 tag 相同）
- 範圍：`prisma/schema.prisma`（4181 行、148 model、40 enum）、`prisma/migrations`（108 個目錄＋`migration_lock.toml`）、加密與 backfill、備份還原 runbook、staging migration workflow（#430／#432）、Supabase 設定
- 方法：靜態閱讀與腳本分析（Python 解析 schema 與 migration SQL），未連任何資料庫（含 staging／Supabase），未讀 `.env*`。Skill 工具不可用，依一般 PostgreSQL 最佳實務判斷。

- 嚴重度定義：BLOCKER＝封測前不修會造成無法回復的資料或金流損失；MAJOR＝有證據的資料完整性／可回復性缺陷；MINOR＝防禦縱深、效能推估或維運風險；NIT＝文件與整潔。

## 前言：整體判斷

資料層的「寫入正確性」做得相當紮實。複合租戶 FK（`[vendorId, id]`）大量使用，金額一律是 `Int` 分（只有 `Live.evergreenPreviewRate` 是 `Float`，而且跟金額無關）。冪等鍵大多落在 DB 層：`WebhookEvent(provider,eventId)`、`PaymentTransaction(vendorId,checkoutIdempotencyKey)`、`InventoryReservation.paymentTransactionId`、`AffiliateCommission(vendorId,deduplicationKey)`、`Settlement(vendorId,monthKey)`、各 payout 的月份唯一鍵。migration 沒有 `DROP TABLE`／`DROP COLUMN`／`TRUNCATE`／`DELETE FROM`，也沒有新增沒有 default 的 NOT NULL 欄位。`SET NOT NULL` 都先回填，或有 `RAISE EXCEPTION` 前置檢查，遇到不合規資料就停止部署。

弱點集中在「資料能不能活下來」：
- 沒有 Production 備份或還原證據。
- 刪除 Vendor 會串聯刪除所有財務紀錄。
- 加密金鑰綁在可能被輪替的 CSRF secret 上。
- schema 和 migration 漂移，任何人跑一次 `migrate dev` 就可能拔掉 DB 層的唯一性保證。

### 本軸確認沒有問題的項目（附證據）

- **破壞性 migration：** 排除 baseline 後，`DROP` 只用在重建 FK、索引、CHECK（例如 tenant-ledger 複合 FK 與 `Product_slug_key` 改為租戶範圍）。`SET NOT NULL` 共 5 處，都有回填或前置 `RAISE EXCEPTION`（`20260806090000_affiliate_payout_contract:5-31` 是範例）。沒有任何新增的 NOT NULL 欄位缺 default（腳本掃描結果 0）。
- **資料回填 migration：** 共 12 個 migration 含 `UPDATE`。訂閱退款兩條（`20261006140000`、`20261007002000`）用的條件很保守：要求完整、已處理的退款帳本總和等於付款金額，而且「較新的 active 訂閱優先」。
- **重跑安全性：** Prisma 以 checksum 管理，不會重跑。staging-migrate 先跑 status 再 deploy；歷史分歧或有失敗的 migration 就停止，也不會自動重試（`staging-migrate.mjs:193-212`）。
- **#430／#432：** 只能在受保護的 master 上執行，使用 environment；與 apply workflow 共用 concurrency 群組；URL 主機、project ref、port 都有允許清單；6543 埠會改成 5432 session 模式；強制 `sslmode=require`；`lock_timeout` 5 秒、`statement_timeout` 60 秒；輸出經過允許清單過濾。缺點是沒有 deploy 前備份（B04-10）。
- **冪等與唯一性落在 DB：** webhook、checkout、inventory reservation、affiliate commission、course allocation、各種 payout、settlement 都有 unique。PostPurchaseCredit 的有效唯一性是 partial unique（但它受 B04-04 的漂移影響）。
- **銀行帳號加密：** 有獨立 keyring（v2、key id、decrypt-only、AAD 綁定 vendor／affiliate），也有 rotation 腳本。backfill 會先檢查不完整或已遮罩的列，遇到就拒絕；加上 CAS，可以安全重跑。
- **migration inventory 測試（#427）：** 已不再寫死數量，改為檢查「每個 model 和 migration 目錄都登記在 inventory」。本次實跑 1/1 通過。它只檢查文字是否出現，不偵測 drift（見 B04-04）。

## 給 ROADMAP 的三句結論

1. 封測收真實款項之前，必須先拿到 Production 備份加一次隔離還原的證據（B04-01），並把 `CSRF_SECRET` 明列為「不可輪替、還原必備」的資料根金鑰（B04-03）。目前兩者都沒有，一旦出事，財務資料無法復原。
2. 封測前要修的資料層項目有三個，總共約 3 人日：CI 加 schema↔migration drift 檢查（B04-04）、訂單號改用安全亂數並加 DB 唯一約束（B04-06）、修復 Production 方案 bootstrap（B04-05）。
3. 正式收費前，用前向 migration 把財務表的 Vendor 串聯刪除改成 RESTRICT，並補上帳務 CHECK 與 RLS 防禦縱深（B04-02、B04-07、B04-08），再建立個資刪除與資料保存期限的 runbook（B04-17）。
