# 封測成功指標與量測方式（BETA-METRICS）

- 版本：2026-10-21 建立。目標值沿用 `docs/ROADMAP-v2.md` §4.7，來源沒有寫的數字標為「未定」。
- 相關：`BETA-OPS.md`、`GO-NO-GO.md`、`docs/market-2026Q4/research_notes/台灣直播導購 SaaS 市場研究 2026/c09_icp_jtbd_gtm_interviews.md` 附錄 B。

## 1. 指標

| 指標 | 目標 | 量測方式 | 資料來源 |
|---|---|---|---|
| 每位客戶完成至少 1 場直播或預錄場 | 100% | 每位封測商家在觀察期內的場次數 | 後台場次紀錄；工程端唯讀查詢（見第 2 節） |
| 首場有非親友出席 | ≥ 50% 的客戶 | 首場的真實觀眾數（不含虛擬使用者，D-10） | 報名與入場紀錄 |
| 每位客戶至少 1 筆 Sandbox 訂單，且對帳正確 | 100% | 訂單數、交易數、對帳差異數 | 訂單與付款交易紀錄；O-12 演練的對帳結果 |
| 通知送達率（報名確認信、開播提醒、LINE） | ≥ 95%，失敗皆有紀錄 | 送達數 ÷ 應送數；失敗筆數與原因 | 寄送紀錄頁；LINE 回應（排程 outcome）；`scheduled-jobs` run |
| 首次成功路徑所需時間 | 記錄中位數（基準值，無目標） | 從註冊到第 9 步（見 `GO-NO-GO.md` §3）的分鐘數；從 onboarding 到首場活動的天數 | 主對話與 owner 的紀錄；訪談紀錄欄 |
| S0 事件數 | 0 | 每週計數，依 Issue 標籤 `sev:S0` | GitHub Issue（標籤 `beta`） |
| S1 事件數 | 目標未定（來源未定義） | 每週計數，記錄 24 小時內是否回應 | GitHub Issue（標籤 `beta`、`sev:S1`） |
| 回顧訪談完成率 | 100% | 已完成訪談數 ÷ 已邀請數 | 訪談紀錄 |
| 付費意願與行為證據 | 記錄分布，無目標 | 回顧腳本第 8 題的四個價位；是否願意預付或簽意向書 | 訪談紀錄（行為證據優先於口頭） |

- 首次成功四階（ROADMAP §4.7 的對應）：第一筆報名 → 首場有非親友出席 → 首筆付費訂單且對帳正確 → 提醒成功送達並被點開。
- 「被點開」的量測來源未在文件中定義，需工程端確認 LINE 或 Email 是否能取得開啟紀錄；取不到就只記送達，不記開啟。

## 2. 資料來源與查詢原則

- 後台頁：場次、報名、訂單、寄送紀錄等後台頁，頁面路徑與名稱由工程端於封測前確認並補入本節（目前來源未列出確切路徑）。
- SQL 唯讀查詢：
  - 由工程端依 `prisma/schema.prisma` 撰寫，經 owner 同意後，在 staging 以唯讀連線執行。本文件不寫 SQL。
  - 查詢範圍限封測商家與合成資料，只回計數，不回買家個資。
  - 不走 Supabase connector 的 `execute_sql`。依 ROADMAP §5.4，該工具白名單只允許中繼資料查詢。
  - 不在 Production 執行。
- 排程紀錄：GitHub Actions 的 `scheduled-jobs` run 與 Summary 表（`success`／`failure`／`skipped`）。
- 訪談紀錄：訪談者自行記錄，只存內部位置，不進 repo。
- 去識別化原則：所有指標只用計數與匿名代號（客戶A、客戶B）。不寫買家姓名、Email、電話、訂單內容。

## 3. 每週回顧模板

每週一由主對話撰寫草稿，owner 確認後存入 `STATE.md` 的每日摘要。

```text
# 封測週回顧 第 N 週（YYYY-MM-DD ～ YYYY-MM-DD）

## 數字
- 封測商家數：__ 位（匿名代號：客戶A、客戶B……）
- 完成直播或預錄場：__ 場（商家達標 __／__）
- 真實觀眾（不含虛擬使用者）：__ 人；首場非親友出席商家：__／__
- Sandbox 訂單：__ 筆；對帳差異：__ 筆
- 通知送達率：報名確認 __%、開播提醒 __%、LINE __%；失敗 __ 筆（原因：__）
- 首次成功路徑：中位數 __ 天（樣本 __ 位）

## 事件
- S0：__ 件（Issue 編號：__；是否已止血：__）
- S1：__ 件（24 小時內回應：__／__）
- S2／S3：__ 件（摘要：__）

## 排程與付款
- 排程 run 紅燈：__ 次（outcome 分類：__）
- needs_attention：__ 次（是否已依 runbook §3.1 處理：__）
- 暫停排程：有／無（原因：__）

## 客戶回報主題（匿名）
- 主題 1：__（影響客戶：__）
- 主題 2：__

## 訪談進度
- 腳本 1 完成：__／__ 場（persona：P1 __、P2 __、P3 __）
- 腳本 2 完成：__／__ 場

## 下週決定（最多 3 項，需 owner 決策的標 ⚠️）
1. __
2. __
3. __
```

- 回顧原則：只寫事實與計數；不寫無法驗證的結論。每個 persona 至少 5 場後，才對訪談結果下結論（附錄 B 通則）。

## 4. 訪談排程

來源：`c09_icp_jtbd_gtm_interviews.md` 附錄 B。

### 4.1 封測前探索訪談（腳本 1）

- 腳本：`docs/market-2026Q4/research_notes/台灣直播導購 SaaS 市場研究 2026/c09_icp_jtbd_gtm_interviews.md` 附錄 B「腳本 1：Beta 前探索訪談」。
- 時點：11-01 前。實際日期由主對話與 owner 排定，來源未定日期。
- 對象順序：P1（有自有名單的講師與顧問，優先）→ P2（團購主，驗證適配度）→ P3（小品牌，探索）。
- 每場 30～40 分鐘，先取得錄音同意。不索取密碼、金流後台截圖或客戶個資。
- 紀錄欄：只由訪談者填寫，不問受訪者。

### 4.2 封測後回顧訪談（腳本 2）

- 腳本：同一附錄 B「腳本 2：Beta 後回顧訪談」。
- 時點：2026-12 封測回顧（D-36）前完成。
- 紀錄欄：onboarding 到首場活動天數、首筆訂單日期、LINE 送達與失敗筆數、回退到舊工具的步驟、是否同意預先付款或簽意向書。
- 注意：ROADMAP §4.6 提到回顧腳本「第 11 題」，但附錄 B 的腳本 2 只有 10 題，沒有第 11 題。ROADMAP 建議把標示觀眾反應的問題改為「虛擬使用者的發言有沒有讓你或觀眾感到困擾」。是否修改腳本，由主對話與 owner 決定；本文件不改腳本。

### 4.3 內部每週回顧

- 週期：封測開始後每週一次，使用第 3 節的模板。
- 與 playbook §7 的對應：每週回顧「已修、仍開著、客戶實際踩到的 finding」，作為 ROADMAP-v2 的第一批真實資料。
